# Phase 5 — Wireframe HTML

The wireframe makes the phase-3 design decisions visible in grayscale. It is composed,
not assembled: each section renders the composition named by its `data-layout`, styled as its
own `w-` BEM block in `assets/sections/<layout>.css`. The markup is Bricks-ready from the first line
(skill `bricks-bem-html` class system; `bem_lint.py --prefix w-` runs inside `qa.py`).

## Build architecture

```
wireframe/
├── tokens.py                 THE token source (spec) → assets/tokens.css + handoff/bricks-tokens.json
├── tokens_builder.py         generator, Bricks maths (vendored from bricks-bem-html; never edited here)
├── assets/tokens.css         GENERATED — loads first, identical to what Bricks prints
├── assets/base.css           Bricks theme style: reset, tag typography, [data-surface] token rules, engine
│                             states keyed on data-*, data-brx element defaults, Container (`bem-lint: base`)
├── assets/components.css     every reused class: type, buttons, media, cards, widgets, forms, commerce
│                             (`bem-lint: components`); project components are added here
├── assets/sections/<layout>.css  one stylesheet per section block w-<layout> (+ header.css, footer.css)
├── assets/sections.css       GENERATED by build.py (header first, footer last, others alphabetical)
├── assets/wireframe.js       interaction engine (generic)
├── assets/icons/*.svg        Phosphor regular icons, inlined by build.py
├── _partials/header.html     designed from design-direction §6, lists every nav node
├── _partials/footer.html     designed from design-direction §6
├── _pages/<slug>.html        body fragments — authored, or written by render.py
├── _templates/<family>.html  template for a page family that shares one composition
├── data/<family>.json        one record per page of that family
├── site.config.json          {"archetype": "brand", "css": [assets/tokens.css, base.css, components.css, sections.css]}
├── render.py                 data × template → _pages/<slug>.html (run before build.py)
├── build.py                  fragments + partials → standalone wireframe/<slug>.html
├── clean.py · qa.py         strip authoring notes · static gate (Gate A)
├── bem_lint.py              BEM lint (vendored from bricks-bem-html; qa.py runs it)
├── browser-checks.js        in-page probe for the browser gate (Gate B)
└── <slug>.html               OUTPUT — regenerated by build.py, never hand-edited
```

`build.py` links the stylesheets in `site.config.json` order with `?v=<mtime>` cache-busting
and inlines the partials, so every page opens from `file://`.

Fragment line 1 is mandatory:
```html
<!--META {"title":"…","desc":"…","template":"T:collection","nav":"products"} -->
```
`nav` matches a `data-nav` key in the header; the footer script marks it current.

## Markup contract (`w-` class system, Bricks-ready)

```html
<section class="w-about" id="about" data-layout="about" data-surface="default" data-brx="section"
         data-brx-template="About band" data-brx-template-mode="insert">
  <div class="w-about__container" data-brx="container">
    <div class="w-about__head" data-brx="block">
      <p class="w-about__eyebrow w-eyebrow">Since 1998</p>
      <h2 class="w-about__title w-heading-l">A workshop, <span class="w-phrase">not a call centre</span></h2>
      <p class="w-about__lede w-text-l">Two technicians, one van, every boiler brand.</p>
    </div>
    <div class="w-about__grid" data-brx="block">
      <article class="w-card-feature" data-component="Card: Feature">
        <i data-icon="clock" class="w-icon w-icon--large w-card-feature__icon"></i>
        <h3 class="w-card-feature__title" data-prop="title">Same-day visits</h3>
        <p class="w-card-feature__text" data-prop="text">Call before noon, we come today.</p>
      </article>
      …
    </div>
    <div class="w-photo w-photo--4x3 w-about__photo">Photo · 4:3 · technician at a boiler, daylight</div>
    <div class="w-about__actions" data-brx="div">
      <a class="w-button-primary" href="contact.html" data-component="Button: Primary" data-prop="label">Book a visit</a>
      <a class="w-button-text" href="services.html" data-component="Button: Text" data-prop="label">All services <i data-icon="arrow-right" class="w-icon w-icon--small w-button-text__icon"></i></a>
    </div>
  </div>
</section>
```
```css
/* assets/sections/about.css — Section about (Bricks: Custom CSS of the .w-about classes) */
.w-about { padding-block: var(--layout-section-pad); }
.w-about__container { display: grid; grid-template-columns: minmax(0, 7fr) minmax(0, 5fr); gap: var(--space-xl) var(--layout-gutter); }
.w-about__head { grid-column: 1 / -1; max-width: var(--max-content-width); }
.w-about__grid { display: grid; grid-template-columns: var(--columns-3); gap: var(--layout-gutter); }
.w-about__actions { display: flex; flex-wrap: wrap; gap: var(--space-s); }
.w-about .w-heading-l { max-width: 18ch; }          /* the one allowed override: .w-section .w-component */
@media (max-width: 991px) { .w-about__container { grid-template-columns: minmax(0, 1fr); } .w-about__grid { grid-template-columns: var(--columns-2); } }
@media (max-width: 478px) { .w-about__grid { grid-template-columns: minmax(0, 1fr); } }
```
- `id` = sitemap §3 slug (anchor target); `data-layout` = design-direction §8 name, and the
  section's block class is `w-<layout>`; `data-surface` = the band's surface (`default`, `subtle`,
  `inverse`, or a project surface); `data-brx="section"`. `data-layout` / `data-surface` are metadata
  for QA and the Figma handoff (`body > section[data-layout]`) — **no stylesheet selects `[data-layout]`**.
- **Section › container › elements.** The section is the largest element; its direct children are
  `w-<layout>__container` with `data-brx="container"`. The container's width and side padding come
  from the theme style — sections never set them; vertical padding sits on the section class.
- **Bricks element types:** a box whose children stack or lay out with flex/grid takes
  `data-brx="block"` (Bricks Block, flex column by default); a plain box takes `data-brx="div"`.
- Every top-level element of a fragment is such a section (or a `<dialog>`); the breadcrumb
  sits inside the first section.
- **Every element has its own class**: `w-<layout>__<part>` or a component class. Global classes
  (type `w-heading-*` / `w-text-*` / `w-eyebrow`, `w-photo`, `w-icon`) may sit beside a section element
  class on one element. Exempt: inline phrasing (`strong`, `em`, `br`, `small`…), links inside running
  text, table rows/cells, everything inside one `data-prose` element.
- **Rich text** (articles, legal): one block with its own class and `data-prose`
  (`<div class="w-article__body" data-prose>`); its children need no classes.
- **No shared layout classes.** Sections own their layout: grid for ≥ 2 columns (`var(--columns-N)`
  or fractions on the parent), flex column for one, flex row for inline runs. The old primitives
  (section, wrap, cols, span-N, split*, grid, g-N, row, stack, bento, spacer, `w-layout-*`) fail `qa.py`.
- **A class styles only its element.** `.w-ledger__row`, never `.w-ledger li`, never
  `[data-layout="ledger"] .w-ledger__row`. The one cross-block selector is `.w-<section> .w-<component>`
  (two compounds, descendant), written only in that section's stylesheet — `.w-x__y .w-button-primary`
  or `.w-card-post .w-button-primary` are errors. Context only from the same block
  (`.w-ledger--compact .w-ledger__row`), states `is-*`/`has-*`, `[aria-*]`. Modifiers sit beside their
  base (`w-photo w-photo--4x3`); `x__y` sits inside an element carrying `x`.
- **Surfaces set tokens, components read them.** `[data-surface="inverse"]` sets only
  `background`, `color` and custom properties (`--surface-link`, `--btn-bg`, `--photo-bg`…); never
  `[data-surface="inverse"] .w-button-primary`.
- **Components are the only reused classes** (`assets/components.css`). A root of a §8c component
  carries `data-component="Button: Primary"`; each element whose text, href, image or icon changes per
  instance carries `data-prop="<id>"` inside that root. A Bricks Component instance keeps only its
  component class(es). Every button type is its own class (`w-button-primary`, `w-button-secondary`,
  `w-button-text`, `w-button-icon`); the label is the root's text (`data-prop="label"` on the root).
  Styling stays in classes; behaviour hooks stay `data-*`.
- **Bricks templates.** A section repeated across pages is a Section template:
  `data-brx-template="Name"` + `data-brx-template-mode="element"` (same structure and content →
  Template element) or `"insert"` (same section and container classes, own content: optional parts, list
  lengths, icons and per-instance modifiers may differ). `qa.py` fails mode `element` instances with a different
  class structure or content, mode `insert` instances with different section / container classes or another
  section's element classes inside, and a section-element class only one instance uses that
  `assets/sections/<layout>.css` never styles (a typo?). `pi-*` / `is-*` / `has-*` classes are ignored.
- **Navigation lists** (footer columns, legal links, simple menus) are WordPress menus in Bricks
  (skill `bricks-bem-html`, rule 9): write each list as `ul.w-{block}__menu > li.w-{block}__menu-item >
  a.w-{block}__menu-link` and name its menu in a comment (`<!-- menu: footer-apartmani -->`) so the
  import creates one menu per list.
- Inline `style=""` only for one-off nudges, under the same spacing/type rules as the section CSS;
  a recurring need belongs in the section's stylesheet as a class.

## Token and design-tool contract (qa.py enforces it; Bricks and html-to-figma read it)

The wireframe is the source both the Bricks site and the Figma file are built from. Tokens follow
skill `bricks-bem-html` `references/tokens.md` (Core Framework naming, Bricks Style Manager):
- **One source:** every token is declared in `wireframe/tokens.py`; `python wireframe/tokens.py`
  writes `assets/tokens.css` (first stylesheet) and `handoff/bricks-tokens.json`. No stylesheet defines
  a token in a `:root`/`html` rule; a `[data-surface]` rule may re-point tokens for its section.
  Every token-family `var()` must exist in tokens.css (qa); no `var(--x, fallback)`.
- **Root 62.5 %** (1rem = 10px), fluid range 320 → 1440. Write px or tokens, never your own rem.
- **Container and grid:** the container is the theme style — `--max-screen-width` (1440, border-box)
  with `--container-padding` (fluid 16 → 40); reading columns `--max-content-width`; sections never
  set it. Columns come from each section's own grid (`var(--columns-N)` or fractions such as
  `minmax(0, 7fr) minmax(0, 5fr)`), never 12-column span classes. Ceilings: desktop ≤ 5 · laptop ≤ 5 ·
  tablet ≤ 3 · mobile landscape ≤ 3 · mobile portrait ≤ 2. The Figma grid comes from the container
  tokens (`handoff.py`: 1512 frame = 76 margin + 12 × 84 + 11 gutters × 32).
- **Breakpoints:** `@media` only at the Bricks breakpoints in `tokens.py`, on every site — `max-width`
  1279 (laptop, custom, always) / 991 / 767 / 478; `min-width` = width + 1; JS `matchMedia` the same.
- **Spacing:** padding / margin / gap only `var(--space-3xs … 5xl)`, `var(--layout-*)` or px multiples of 4.
  Borders may be 1–2 px.
- **Type:** `font-size: var(--text-xs … 6xl)` (base × ratio scale) with `line-height: var(--line-height-xs … xl)`
  (unitless). Map each role to a step once (design-direction §5); no `--text-<role>` size tokens — in this
  system `--text-title/body/body-dark/eyebrow/contrast` are **colours**.
- **Colour:** class CSS reads Theme roles first (`--bg-*`, `--text-*`, `--border-*`, `--accent`, `--active`,
  `--hover`, `--focus`, status), then the Neutrals ramps (`--dark-N` flips with the theme, `--all-light-N` /
  `--all-dark-N` never flip — use them on photos and night bands), Brand (`--primary[-l|-d-N]`) last.
  **One colour token per text role** (`.w-eyebrow` → `--text-eyebrow`). Dark mode = the Theme roles' dark values
  under `html[data-brx-theme="dark"]` (`localStorage "brx_mode"`), no per-class dark selectors.
- **Icons:** `<i data-icon="arrow-right" class="w-icon w-icon--small"></i>` (names = `assets/icons/*.svg`,
  Phosphor regular); `build.py` inlines the SVG. No glyph icons (☰ ✕ ♡ → ★ …) in copy, no text in
  CSS `content:` — numbers, arrows and +/− live in markup so the design tool sees them.
  Never style by icon name (`.pi-arrow-right`, `a:has(> .pi-…)`): give the role a class
  (`w-button-text__icon`, `w-card-feature__icon`). In Bricks the same folder becomes one custom icon set and
  every icon an SVG element from it (skill `bricks-bem-html`, rule 8); a component instance that
  changes its icon marks the icon with `data-prop="icon"`.

## Authoring rules

1. **Grayscale only.** No `<img>` — image slots are `w-photo` elements (ratio modifier
   `w-photo--4x3` …, plus a section element class) whose text is the art
   direction from the content file ("Photo · …"), in the site language. That brief is kept on
   purpose (it seeds image-generation prompts later) and holds **everything** about the image:
   subject, role, setting, ratio, light. Never add a visible caption, credit line or small note
   under or beside an image slot ("Wound-care nurse · home visit") — it reads as a leftover
   note. Qualifiers that matter (e.g. "in vitro") go into the body text or a table heading.
2. **Copyable text.** Real sentences, verbatim from `content/*.md`; never lorem.
3. **Every link resolves to a real page.** Relative `.html` in the same folder. There are no
   placeholder pages: a linked page is authored, generated, or the link is removed.
4. **Breadcrumb** on every page except home (unless design-direction §6 says otherwise, e.g.
   placed inside a hero); last crumb unlinked.
5. One `<h1>` per page; sections `<h2>`; items `<h3>` or `<p class="…__title">` — no level jumps.
6. Interactive controls are `<button type="button">`, never `<a href="#">`.
7. No `<style>` or `<script>` in fragments; widgets come from the engine.
8. Only engine widgets allowed for the archetype (`interactions-contract.md`).
9. **Headings break by meaning — never a lone word on the last line, never a line that ends
   one sentence and starts the next.** `base.css` balances every heading
   (`text-wrap: balance`), but balance alone still strands words in narrow columns and splits
   sentences ("Two care / areas. One / standard of care."). Author the breaks:
   - `&nbsp;` after short function words (a, an, the, and, or, of, to, for, in, on, at, by,
     with, from, into, your, our, its, their, &) and between the last two words of each
     sentence: `One standard of&nbsp;care.` Keep every glued chain ≤ 18 characters or it
     overflows narrow columns; release the leftmost function-word glue first, the
     last-two-words glue last. No glue after a comma.
   - Two or more sentences: wrap each in `<span class="w-phrase">` (inline-block), so lines break
     only between sentences. Use `.w-phrase` also for a group that must stay whole but is too long
     to glue safely (product variant after the brand: `Nür <span class="w-phrase">Premium Maxi</span>`)
     — it wraps inside itself instead of overflowing.
   - Data-driven headings: render heading fields raw (`{{&benefits_heading}}`) so the data file
     can carry `&nbsp;` and `.w-phrase`; split product names into `brand` + `variant` fields for the
     H1 and every heading that repeats the name.
   - Arrow suffixes on titles are icons glued with a no-break space:
     `Our apartments&nbsp;<i data-icon="arrow-right" class="w-icon w-icon--small"></i>`.
   - Not `text-wrap: pretty` on headings: Chrome only reshapes the last lines of long paragraphs,
     leaves 2–3-line headings as they are (measured on a 43-page build: ~2× the defects of
     `balance`) and Firefox lacks it. It is fine for body copy.
   Gate B fails any heading with a lone last word, a split sentence or an overflowing word.

## UI mockup refine (phase 7)

Colour, typefaces, type scale, spacing values and component skins come in phase 7: token values in
`tokens.py`, `@font-face` and theme typography in `base.css`, component skins in `components.css`,
section-specific looks in `assets/sections/<layout>.css`, all from `design.md`
(`references/phase-7-ui-refine.md`); `"style": true` in `site.config.json` marks the refine as done and
makes `build.py` mark pages `<html data-style="on">`.

## Photo layer (only when the user asks for real photos, e.g. on listing cards)

Use only the client's own photos (their site, API or shared folder) — never stock or a
competitor's. Download a fixed, documented subset (e.g. first 4 per item, owner order, ~1024 px)
into `wireframe/assets/photos/{slug}/NN.jpg` with a manifest (`research/photos.json`: source URL,
size). Keep `w-photo` and its brief (future alt text): the slot gets `data-photo="{slug}/NN"` and a
generated `assets/photos.css`, loaded after `sections.css`, sets `background-image`, hides the brief
(`color: transparent`) and the hatch. No `<img>`, so qa and the probe still pass; removing the
stylesheet from `site.config.json` returns the grayscale wireframe. Verify layout identical with
style + photo layers on vs off, and that every `background-image` URL resolves.

## Header and footer

Design them from design-direction §6 — overlay or solid, what the bar holds, how the menu
opens, mobile pattern, footer composition. Start from the skeleton in `_partials/`
(`commerce` archetype: the commerce templates). They must link every page of the IA table
(dropdown entries, utility row, footer columns), legal pages and contact data; footer
columns mirror the header groups. Styles live in `assets/sections/header.css` / `footer.css` (blocks
`w-header`, `w-nav-panel`, `w-footer`, `w-to-top`). Measure where the bar would wrap
(1024 / 1280 / 1440) and switch to the menu button at the Bricks breakpoint just above it (991, or a
custom `laptop` 1279 every site has), and anchor dropdown panels so they
stay inside the viewport — the browser probe checks both. Dropdowns are the engine's
click widget (`data-menu-toggle` + `data-menu`, interactions-contract §10c), never `:hover`-only.

Keep the `data-chrome` hooks — the Figma Header/Footer components are filled from them:
header `brand` (logo link), `nav` (main nav container), `utility` (utility row), `cta` (primary
CTA); footer `tagline`, `contact` (one child element per line), `footer-col` (heading + links,
one per column), `legal`, `legal-links`. **No review bar / page index above the header** (`wf-bar`):
reviewers move through the wireframe with its own header, footer and links, exactly as visitors
will — a bar of shortcuts hides unreachable pages and is noise in screenshots and Figma (`qa.py`
rejects it). Review-only markup, if ever needed, goes between `<!--wf:review-->` and
`<!--/wf:review-->`; `python wireframe/build.py --final` drops it for client and handoff builds.

## Catalogue widgets (commerce, or brand sites with a genuine browse need)

Render every group and value from `sitemap.md §4` as real checkboxes wired to `data-catalog`.
Prices only when the archetype is `commerce`: plausible, local format, 1–2 real ones kept,
a few struck-through sale prices; an empty `.w-card-product__price` fails QA.

## Every linked page is a real page

No stubs, no "this page will contain…" tables, no "coming soon". For each page in
sitemap §1 that is linked from the build:

| Page kind | How it is produced |
| --- | --- |
| Concept / representative pages | authored fragment, composition from design-direction §7 |
| Other single pages (about, hub, legal, utility…) | authored fragment, composed in phase 3 from the same layout catalogue — usually reusing layouts, adding few new ones |
| Families sharing a composition (products, services, locations, team roles…) | `_templates/<family>.html` + `data/<family>.json` → `python wireframe/render.py` |
| Pages without real content yet (blog with no articles) | not built and **not linked**; listed as phase 2 in the sitemap |

`render.py` syntax: `{{field}}` (escaped), `{{&field}}` (raw), `{{a.b}}` / `{{list.0.x}}`,
`{{#each list}}…{{/each}}` with `{{.}}`, `{{@n}}`, `{{@nn}}`, `{{@last}}`,
`{{#if x}}…{{else}}…{{/if}}`, `{{#unless x}}…{{/unless}}`. A missing field stops the run with
the page and field name. Generated fragments carry a `wf:generated` marker; edit the data or
the template, never the output. The data file is the content file for that family.
A class that depends on data never splices template code into the class value (`class="w-slide{{x}}"` breaks
`bem_lint.py`): repeat the whole attribute in each branch, with spaces around the tags and after the tag name —
`<div {{#if active}} class="w-slide is-active" {{else}} class="w-slide" {{/if}} id="{{id}}">`.
